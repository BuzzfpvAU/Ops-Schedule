# V2 UI — timeline interface (taskz.id)

> **Date:** 19 Sep 2026
> **Brief (Grant):** "Take a step back from the current UI and develop a new interface, but keep a lot of the work previously done." Three distinct timeline views — projects, equipment, team — with dates across the top and rows down the side, kept within states.
> **Decisions taken with Grant before building:**
> 1. A **job is a project** — no project layer above jobs, no migration.
> 2. V2 is a **separate front end** against the existing API, not a replacement for the v1 UI.
> 3. **Day columns with a zoom control** (day / week / month).
> 4. A fourth view is coming later; three are in scope now.

---

## 1. Shape of the change

V2 is a second Vite app in `client-v2/`, served at `/v2`. The v1 client at `/` is untouched
— same database, same API, same session cookie, so a user signed in to one is signed in to
the other, and `/v2` has a link back.

Nothing was rewritten on the server. The three views are projections of data the API already
returns, because `schedule_entries` is already a universal *(entity × date × job)* table and
equipment already lives in `team_members` with `is_equipment = 1`.

| V2 needs | Already existed |
|---|---|
| Job rows with spans | `GET /api/jobs` → `roster_start`, `roster_end`, `crew_count`, `state`, `planned_start/end` |
| Bookings in a window | `GET /api/schedule?start&end` |
| People and equipment | `GET /api/team-members`, `…/equipment` |
| Job detail | `GET /api/jobs/:id` |
| Leave / TOIL / notes | `POST /api/schedule/quick`, `DELETE /api/schedule/:id` |
| Travel-time adjustment | `POST /api/jobs/equipment/:id/booking` (`edge`, `delta`) |

**One endpoint was added.** `GET /api/equipment/bookings?start&end` is the reverse of the job
card: given a window, which `job_equipment` assignment owns each item's booked days. The
equipment timeline needs it to adjust travel pads without first opening the job. It filters to
assignments whose booked span overlaps the window and drops unbooked ones, which have no bar.

## 2. The shared engine

`components/Timeline.jsx` is the Gantt engine all three views render through. It is a
generalisation of the geometry already proven in `client/src/components/JobPlanner.jsx`.

- **One scroll container, two sticky axes.** The date header pins with `position: sticky; top`,
  the label column with `sticky; left`. A single container scrolls both ways, which avoids the
  two-container scroll-sync that tends to judder.
- **Columns are always one day.** Zoom changes only pixels-per-day (34 / 13 / 4), so bar
  geometry is identical at every level and nothing has to be re-bucketed when zooming.
- **Callers own their rows.** A view supplies groups of rows, each row its own bars with
  absolute day indices and a lane. What may overlap differs per view, so lane assignment is the
  caller's job via `lib/model.js`.
- **Bars clip to the window** rather than disappearing, so a project that started before the
  visible range still draws, cut off at the edge.

`lib/model.js` holds the data shaping — merging entries into bars, lane stacking, conflict
detection, bucketing rows under a heading. `lib/dates.js` holds ISO date maths and the zoom
table. Both are pure and carry the test suite (37 tests in `client-v2/test/`).

### Two bugs worth recording

**Interleaved bookings fragmented their bars.** Merging in a single date-ordered pass looks
right, but when a row carries two overlapping jobs their entries interleave by date, and each
switch ended the run — so one continuous booking drew as several fragments. `buildBars` now
partitions by key first, then merges within each partition. Regression tests cover the two- and
three-job overlap cases.

**Quick-entry jobs leaked into the project view.** `POST /api/schedule/quick` creates a real
`jobs` row to back leave, TOIL, unavailability and each distinct note, so they come back from
`GET /api/jobs` looking like projects. `isQuickJob()` filters them out of the project timeline
and the unallocated list by code (`TOIL`, `LEAVE`, `NOT-AVAIL`, `NOTE-*`).

## 3. The three views

### 3.1 Projects — `ProjectsView.jsx`

Rows are jobs, grouped by the state managing them (`jobs.state`, which the server already
derives from the lead's base location). Two bars per job:

- **Planned window** (`planned_start`/`planned_end`) as a dashed outline — the intent.
- **Rostered days** as a solid bar — what is actually booked, split per contiguous run.

Where the two disagree, the gap is the point of the view. A `2/3` badge marks a job short of
`crew_size`. Status filter across Open / Planning / Confirmed / Active / All. Clicking a row or
bar opens a drawer with the job's crew and kit from `GET /api/jobs/:id`.

### 3.2 Equipment — `EquipmentView.jsx`

Rows are equipment items; bars are the jobs they are booked to, merged per job so a status
change mid-booking is not noise. Overlapping bookings stack into lanes and both get a red
outline, with a `CLASH` tag on the row label — the timeline shows availability as the gaps.

**Home-base toggle**, as asked: on, rows group by `location` (the item's home state); off, by
`equipment_category`. Also a booked-only filter and a text filter.

**Travel time** is the pad either side of a booking. The drawer's steppers call the existing
booking endpoint, which reserves or releases real days — so extending travel genuinely makes
the item unavailable to another job while in transit, and the response's conflict list surfaces
as a warning when that extension collides with something else.

### 3.3 Team — `TeamView.jsx`

Rows are people grouped by base state, carrying job allocations and the non-job entries — leave,
TOIL, notes, unavailability — on the same line, because whether someone can take a job depends
on both.

**Unallocated work** leads the view as its own group: jobs planned but short of crew, drawn as
dashed "needs crew" bars over their planned window, with a `+n` badge for how many are missing.
The work waiting for people sits in the same timeline as the people.

Clicking a day or bar opens a day panel listing what is on that day and offering note, TOIL,
leave and unavailable via `POST /api/schedule/quick`. Permissions follow the server: admins edit
anyone, members edit their own row, viewers edit nothing. Job allocation itself stays on the job
card — this panel is for the non-job entries.

## 4. What was verified

Driven in a real browser against a seeded database, all three views:

- Zoom levels render (90 / 209 / 461 day columns at 34 / 13 / 4px).
- Labels stay pinned at x=0 through horizontal scroll; groups collapse.
- Adding TOIL persists and removing it restores the day.
- Extending equipment travel time moved a booking from 26 Sep to 27 Sep and correctly reported
  the new clash with AU-2602, then reverted.
- Home-base ↔ category grouping and the booked-only filter both re-bucket correctly.
- No console errors; no page overflow at 430px, where the label column steps down to 170px.
